# ADR 0026: 접근 규칙 — 보는 건 누구나, 새로 분석하는 건 로그인 후

- 상태: Accepted (2026-10-25)
- 관련: `docs/strategy.md` 9절 13번 (백엔드 인증·요청 수 제한 없음), ADR 0024 (graph-v1)

## Context
홈 화면의 두 진입 경로가 서로 다른 규칙을 따르고 있었다 [확인: 코드와 브라우저, 2026-10-25].
- "예시 지도 보기" → 로그인 없이 `/analyze`
- "시작하기" → 로그인하지 않았으면 `/login` (화면이 `localStorage` 토큰 유무만 보고 판단)
- `/analyze` 자체에는 로그인 검사가 없다. 주소를 직접 치면 누구나 들어간다.
- 회원가입이 막혀 있어 "시작하기"로는 새 방문자가 분석 화면에 갈 수 없었다.

또 [비공개: 운영 설정 상태] 분석 요청이 실패했고, 화면에는 백엔드의 영어 오류 원문이 그대로 보였다.

## Decision
1. **보는 건 누구나.** 홈의 "시작하기"와 "예시 지도 보기" 모두 로그인 여부와 상관없이 같은 탭에서 `/analyze` 로 간다.
   "시작하기"는 `/analyze?start=1` 로 가서 입력창에 바로 포커스한다 ("예시 지도 보기"는 포커스하지 않음 — 휴대폰에서 키보드가 뜨지 않게).
2. **새로 분석하는 건 로그인 후** — 다만 이 요구는 **백엔드에서** 한다 (아래 3).
   화면은 분석 요청을 그대로 보내고, 백엔드가 503 을 주면 "지금은 예시 지도만 볼 수 있어요. 직접 분석은 준비 중이에요." 를 보여 준다.
3. **화면에서 막는 건 보호가 아니다.** 화면의 버튼·이동 규칙은 누구나 주소창이나 API 호출로 건너뛸 수 있다.
   실제 로그인 요구는 백엔드 `/api/analyze` 에서 **토큰 검증**과 **요청 수 제한**으로 해야 한다 (`docs/strategy.md` 9절 13번).
   [비공개: 현재 보호 상태]

## 순서 (운영)
1. 백엔드 보호를 먼저 넣는다: 토큰 검증 의존성, IP별 요청 수 제한, 입력 길이 제한 (9절 13번의 구현 제안).
   회원가입도 함께 고쳐야 로그인 요구가 의미를 가진다.
2. 오류 로그가 콘솔에 보이게 고친다 (9절 14번, 우선순위 높음).
3. [비공개: 운영 설정 순서]
   백엔드 보호 없이 분석 기능을 열면, 화면 규칙과 상관없이 누구나 분석을 호출해 외부 AI 비용을 쓸 수 있다.

## Consequences
- 새 방문자도 홈에서 바로 분석 화면과 예시 지도를 볼 수 있다. 회원가입이 막혀 있어도 서비스가 무엇인지 보인다.
- 화면에는 로그인 판단 코드가 없다. 로그인이 필요해지면 백엔드가 401 을 주고, 화면은 그때 로그인 안내를 보여 주도록 바꾼다 (아직 401 처리는 없음).
- [비공개: 백엔드 오류 문구 관련]

## 갱신 (2026-10-25): 로그인 입구를 인증 묶음 작업 전까지 숨김 (B안)
- **이유**: 회원가입이 막혀 있어 새로 로그인할 수 있는 사람이 없고, 분석 화면은 이미 누구나 들어간다. 그래서 로그인 버튼은 막다른 길이었다. [비공개: 인증 기능 상태]
- **한 것** [확인: 브라우저, 토큰이 있을 때와 없을 때 모두]
  - 상단 내비의 로그인·로그아웃 버튼을 숨겼다.
  - `/login`, `/register`, `/reset-password` 로 직접 들어오면 "로그인과 회원가입은 준비 중이에요. 예시 지도는 지금 바로 볼 수 있어요." 와 `/analyze` 링크를 보여 준다.
  - 로그인 화면의 "비밀번호를 잊으셨나요?" 링크를 숨겼다.
  - 페이지와 폼 코드는 지우지 않고 `frontend/lib/features.ts` 의 `AUTH_ENABLED`·`PASSWORD_RESET_ENABLED`(둘 다 false)로 감췄다. 안내 화면은 `frontend/components/AuthComingSoon.tsx`.
  - 분석 버튼 이름을 "분석하기"에서 "지도 그리기"로 바꿨다 (디자인 시안과 맞춤).
- **숨긴 것은 보호가 아니다.** 보호는 위 Decision 3 대로 백엔드에서 한다. [비공개: 현재 보호 상태]
- **다시 여는 조건** (인증 묶음 작업, 9절 13번에서 모두 갖춘 뒤 `AUTH_ENABLED` 를 켠다)
  1. 회원가입 수정
  2. 백엔드 토큰 검증 (`/api/analyze` 등 보호할 API 에 의존성으로)
  3. 요청 수 제한 (IP별, 로그인·회원가입 시도 포함)
  4. 비밀번호 재설정 (백엔드 API 와 메일 발송. 갖춰지면 `PASSWORD_RESET_ENABLED` 도 켠다)
  5. 가입 여부를 드러내지 않는 메시지 (로그인 실패·재설정 요청·중복 확인에서 "없는 계정"인지 알 수 없게)
- **그때 검토할 것**: 직접 구현과 외부 인증 서비스(예: Google 로그인 같은 OAuth, Neon 의 Better Auth 기반 인증 등)를 비교한다. 비교 항목: 비밀번호 저장·재설정·메일 발송을 직접 맡을지, 비용, 데이터가 어디에 저장되는지, FastAPI 백엔드에서 토큰을 검증하는 방법, 기존 `users` 테이블과의 이전. 각 서비스의 기능과 조건은 그때 공식 문서로 확인한다 (이 메모를 쓸 때 확인하지 않음).

## 갱신 (2026-11-04): 백엔드 인증 경로도 닫음
- **이유**: 위 원칙("숨긴 것은 보호가 아니다") 그대로다. 화면에서 로그인 입구를 숨겨도, 백엔드의 로그인·회원가입 경로는 직접 호출하면 응답했다.
- **한 것**
  - 백엔드 신호 `ATLAS_AUTH_ENABLED` 를 두었다. 기본은 꺼짐이고, 정확히 `"1"` 일 때만 인증 경로를 붙인다. API 문서 경로를 닫을 때와 같은 방식이다.
  - 꺼져 있으면 `/auth/login`·`/auth/register` 는 404 를 준다.
  - 테스트를 먼저 쓰고(고치기 전 실패 확인) 고쳤다. 신호가 없을 때, `"0"`·`"true"`·빈 값일 때 404 이고, `"1"` 일 때만 경로가 붙는다.
- **확인** [2026-11-04, 운영 배포 뒤]: 빈 입력 POST 로 `/auth/login`·`/auth/register` 모두 404, `/` 는 200. 계정은 만들지 않았다.
- **다시 여는 조건**: 위 "다시 여는 조건" 1~5 를 갖춘 뒤 백엔드 신호와 화면의 `AUTH_ENABLED` 를 함께 켠다.

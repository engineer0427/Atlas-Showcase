# ADR 0025: 다리 후보 판정 v1 과 연결 이유 원칙

- 상태: Accepted (2026-10-25)
- 관련: ADR 0024 (graph-v1 응답 형식), `docs/strategy.md` 9절 5번
- 성격: **v1 휴리스틱, 정답 기준 검증 전.** 아래 기준은 화면의 노이즈를 줄이려는 것이고, 정답(실제로 분야를 잇는 문서)과 비교해 검증하지 않았다. 숫자는 벤치마크 질의 8개의 진단 결과를 보고 정했으므로 그 8개에 맞춰졌을 위험이 있다. 평가 방법 설계는 나중 과제다 (`docs/strategy.md` 9절).

## Context
개발 DB([비공개: 개발 환경]) 실제 연결(2026-10-25)에서 검색 순위는 벤치마크 v1 과 같았지만 화면에 세 가지 문제가 보였다. 오프라인 진단 도구 `scripts/diagnose_graph.py` (운영과 같은 코드 경로, 저장된 임베딩, 질의 8개, 결과 10개)로 원인을 확인했다.

| 문제 | 진단 (고치기 전) | 원인 [코드로 확인] |
|---|---|---|
| 다리 문서가 너무 많음 | 질의마다 10개 중 6~10개, 커뮤니티 0개 | 매개 중심성을 논문–논문 엣지 + **저자 노드**(질의당 27~68개)를 합친 그래프에서 계산. 저자 노드는 자기 논문에만 붙어 거의 모든 논문이 통로가 됨. 판정은 절대 문턱 0.08 하나. 커뮤니티는 기본값이 꺼짐(`ATLAS_COMMUNITY_ALGO=none`)이고, `louvain` 은 패키지가 없어 조용히 빈 값 |
| "함께 쓰는 단어"에 and·for·are | 8개 질의 전체에서 and 244, for 149, are 109 엣지 | 불용어 제거 없이 3자 이상 토큰의 교집합을 알파벳순으로 자름 |
| "결론이 다를 수 있음" | 8개 중 6개 질의에서 2~8개 | 두 문서를 비교하지 않음. 한쪽 초록에 however·despite 같은 표현이 있으면 점수가 붙고, 이유 판정에서 가장 먼저 선택됨 |
| "방법이 겹침"이 가장 많음 | 질의당 2~30개, 8개 중 7개 질의에서 가장 많은 이유 (DB 의 `method_terms` 는 비어 있음) | 한쪽 초록의 문장 패턴만 보는 deep 점수(≥0.25)로 이유를 정함. 두 문서가 함께 가진 용어가 없어도 붙음 |

## Decision
1. **다리 후보 (v1)** — `backend/engine/graph_builder.py` `mark_bridge_nodes`, 호출 `src/atlas/insight_engine.py`
   - 논문–논문 엣지만으로 계산한다. 저자·방법·데이터셋 노드는 넣지 않는다 (이종 연결은 graph-v2 과제, ADR 0024).
   - 커뮤니티: networkx 내장 `greedy_modularity_communities` (연결 강도 = 유사도). 결과가 매번 같고 새 의존성이 없다. `ATLAS_COMMUNITY_ALGO=louvain` 이면 networkx 내장 louvain(seed 0), `none` 이면 계산하지 않는다(다리 후보 0개).
   - 조건 (모두): ① 이웃이 2개 이상의 커뮤니티에 걸침 ② 매개 중심성 > 0 이고 결과 안에서 상위 20% (`ATLAS_BRIDGE_TOP_FRACTION`) ③ 결과당 최대 2개 (`ATLAS_BRIDGE_MAX`). 커뮤니티가 1개뿐이면 0개.
   - `bridge_score` 는 매개 중심성 그대로. 이전의 절대 문턱 `ATLAS_BRIDGE_THRESHOLD` 는 쓰지 않는다.
   - 화면·문서에서는 "다리"라고 단정하지 않고 "묶음을 잇는 문서 후보"라고 쓴다.
2. **연결 이유 원칙**: 두 문서가 실제로 함께 가진 근거(공유 방법 용어, 공유 데이터·실험 절차 용어, 인용 신호, 공유 단어)가 확인된 이유만 고르고 화면에 보인다. 없으면 "내용이 비슷함".
   - 엔진 `_pick_reason` 과 화면 변환 `graph_view._supported_reason` 둘 다 이 원칙을 따른다 (화면 쪽은 안전장치).
   - deep 점수(한쪽 문장 패턴)와 `contradiction_signal` 은 이유로 쓰지 않는다. graph-v1 라벨에서 "결론이 다를 수 있음"을 뺐다.
   - 화면 근거에서 인용문(한쪽 초록의 문장)을 뺐다. 겹침의 근거가 아니고, 출판사 저작권 문제도 줄어든다.
   - 엔진 내부 증거(`evidence.contradiction_signal`, `deep_scores`, 가설 정렬)는 그대로 둔다.
3. **함께 쓰는 단어**: 표준 영어 불용어 + 학술 상투어(algorithm·data·based·method 등, 진단 빈도로 정함)를 빼고, 숫자만인 토큰을 빼며, 3자 이상(약어 보존). 최대 5개.
   - 정렬 (2026-10-25 갱신): **키니스** = (이번 결과 안에서 그 단어를 쓴 문서 수) × ln((코퍼스 문서 수 + 1) / (코퍼스에서 그 단어를 쓴 문서 수 + 1)), 높은 순, 동점은 알파벳순. 이번 결과 안에서 자주 쓰이고 코퍼스 전체에서는 드문 단어(주제어)가 앞에 온다. 클래스 기반 TF-IDF 와 같은 표준 방식이다.
   - 처음 정한 "결과 10개 안에서 드문 단어 먼저"는 finally·found·improved·approximately 같은 일반 단어를 앞세워 바꿨다. 단어를 하나씩 불용어에 넣는 방식은 질의 8개에 맞추는 것이라 쓰지 않았다.
   - 코퍼스 빈도: 엔진이 DB 에서 전체 논문의 제목·초록을 읽어 같은 토크나이저로 세고 프로세스 메모리에 둔다 (`src/atlas/insight_engine.py` `_corpus_word_df`). 논문 수나 마지막 id 가 바뀌면 다시 센다. 새 의존성·스키마 변경·DB 쓰기 없음.
   - **DB 가 없을 때**(라이브러리 단독 사용, 또는 읽기 실패)는 이번 결과 안 빈도가 높은 순으로 대체한다. 읽기에 실패하면 rollback 해서 다음 명령을 막지 않는다.
   - **C안(키니스)은 질의 3개(costa2002, hitachi_isscc2015, komorowski2018)의 예시 비교로 고른 것이고 정량 평가는 하지 않았다.** 비교한 대안: 결과 안에서 드문 순(이전), 코퍼스 IDF 만 (코퍼스에서 드문 순 — approximately 처럼 코퍼스에 드문 일반 단어가 앞에 와서 버림), 일반 영어 고빈도 목록 (`wordfreq` 같은 새 의존성과 데이터 라이선스 확인 필요, heart·rate·energy 같은 주제어도 일반 영어에서 흔해 함께 밀려나 버림).

## 결과 (고친 뒤 진단, 2026-10-25) [확인: `scripts/diagnose_graph.py`]
- 상위 10개 순서: 8/8 질의가 `results_v1.json` 과 같음 (검색 순위 불변).
- 다리 후보: 모든 질의에서 10개 중 2개, 커뮤니티 모든 질의에서 2개.
- 화면 라벨 (8개 질의 엣지 258개): 핵심 단어를 함께 씀 198, 방법이 겹침 55, 내용이 비슷함 3, 데이터·실험 절차가 겹침 2. 근거 없이 이유가 붙은 엣지 0, 인용문 0.
- 함께 쓰는 단어 상위: filter, radar, kalman, non-gaussian, signal, filtering, rate, particle … (드문 순 정렬일 때)
- 키니스 정렬로 바꾼 뒤 (같은 날): 상위 filter, kalman, radar, energy, non-gaussian, optimization, filters, heart, parallel, architecture. 회귀 검사 8/8 일치, 다리 후보·커뮤니티·연결 이유 개수는 바뀌지 않음.

## 한계와 주의
- **다리 후보가 모든 질의에서 정확히 2개다.** 결과 10개가 늘 커뮤니티 2개로 나뉘고, 매개 중심성 상위 2개가 경계 조건도 만족했다. 즉 지금 데이터에서는 기준이 "상위 2개"와 거의 같게 동작해 **구분력이 확인되지 않았다**. 숫자를 이 8개에 맞춰 다시 조정하지 않고, 정답 세트로 평가한 뒤 정한다.
- "방법이 겹침" 55개 중 43개는 공유 용어 `kalman filter` 다. 용어 사전(`DEFAULT_METHOD_TERMS`)이 부분 문자열로 찾아 `attention` 처럼 일상어와 겹치는 항목도 있다 (6개). 사전 품질은 별도 과제.
- 결론 차이 탐지는 두 문서의 주장을 비교하는 방식으로 새로 설계해야 한다 (나중 과제).
- (해결, 위 3번 갱신) "결과 10개 안에서 드문 단어 먼저" 정렬은 finally·found·improved·approximately·discuss 같은 일반 단어를 앞세웠다 [확인: costa2002 결과].
- **키니스의 약점**: 같은 주제어가 여러 연결에 반복돼 연결마다 다른 점이 덜 드러난다. 고친 뒤 진단에서 엣지 258개 중 26개가 같은 질의의 다른 엣지와 단어 목록이 완전히 같았다 (예: see2016_drfm 의 앞 3개 연결이 모두 radar, deception, jamming, signal, detection). 연결별 차이를 드러내는 방법은 나중 개선 과제.
- **코퍼스가 작으면 IDF 가 거칠 수 있다.** 지금 코퍼스는 128편(벤치마크 코퍼스)이다. 일반 단어가 줄었지만 남아 있다: 진단에서 approximately·discuss·purposes·six·capable 이 각각 엣지 1개의 단어 목록 끝쪽에 나왔다 (공유 단어가 적은 연결).
- **규모**: 코퍼스 빈도를 셀 때마다 전체 논문의 제목·초록을 읽으므로 수백 편 규모용이다. 커지면 미리 계산한 테이블(단어별 문서 수, 적재 때 갱신)로 옮긴다. 캐시 키(논문 수, 마지막 id)는 기존 논문의 제목·초록 수정을 감지하지 못한다.

## Alternatives
- 절대 문턱만 올리기 (예: 0.08 → 0.3): 저자 노드가 매개 중심성을 부풀리는 원인을 그대로 두므로 버림.
- 커뮤니티 없이 매개 중심성 상위 N 개: "서로 다른 묶음을 잇는다"는 뜻을 담지 못해 버림.
- `python-louvain` 패키지 추가: networkx 내장으로 충분해 새 의존성을 피함.
